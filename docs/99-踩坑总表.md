# 踩坑总表

按「你会看到的报错」索引。报错原文照抄，可以直接全文搜索。

每一条都是真实撞过的，不是推测。

---

## A. 权限与系统（最容易被误判）

### A1. `touch: /Applications/QQ.app/Contents/Resources/app/package.json: Operation not permitted`

**看起来是**：文件权限不够 → `sudo chmod` / `chown` 就行了。

**真正原因**：不是文件权限，是 macOS 的 **TCC · App Management**（系统设置 → 隐私与安全性 → App 管理）。它拦的是**发起写入的那个进程**，不是被写的文件。所以：

- `ls -l@` 看这个 app **没有 `restricted` 标志**，不是 SIP 的问题
- 用 `sudo` 也没用，root 一样被拦
- 从 Terminal 里执行**就过得去**——因为 Terminal 已经被授予了「App 管理」

**修法**（二选一）：

1. 让你的终端拿到权限：系统设置 → 隐私与安全性 → **App 管理** → 打开你的终端（Terminal / iTerm）
2. 或者绕开：所有对 `/Applications/QQ.app` 的写操作，交给 Terminal 执行：

```bash
osascript -e 'tell application "Terminal" to do script "sudo bash /path/to/script.sh"'
```

**踩坑延伸**：如果发起进程是 IDE、桌面应用或某个 agent，它永远拿不到这个权限，唯一出路是走 Terminal。

---

### A2. 向 `~/Library/Containers/com.tencent.qq/Data/Documents/` 写入被拒

**报错**：`你没有将文件"napcat"保存到文件夹"Documents"中的权限。`

QQ 的容器目录同时受 **TCC（完全磁盘访问权限）**和**沙盒**管。给终端加「完全磁盘访问权限」之后才能读写。注意改完要**重启那个 app**才生效。

---

### A3. NapCat 安装器显示「程序入口 ✅ NapCat」，但 QQ 启动后完全没加载

**看起来是**：装好了，是不是漏了哪一步。

**真正原因**：安装器的状态是它**自己的记录**，不是实际状态。三条都成立才会真正加载：

1. `/Applications/QQ.app/Contents/Resources/app/package.json` 的 `main` 字段被改成 `./loadNapCat.js`
2. `loadNapCat.js` 里 `process.argv.includes('--no-sandbox')` 为真（启动参数带 `--no-sandbox`）
3. QQ 启动时不会把它还原

**实测结论**：QQ 7.0.2 上第 1 条就没成——`main` 一直是 `./application.asar/app_launcher/index.js`，文件 mtime 停在启动时刻（说明是 QQ 自己写的），安装器根本没写过它。而且 `loadNapCat.js` 的 `installPathPkgJson.main` 修改逻辑，指向的字段在 asar 里，改不动。

**别在这上面耗时间**，去看 `01-为什么难.md` 的第三条路。

## B. 协议端

### B1. Lagrange：`Signer server returned a NotFound` / `sign.lagrangecore.org` 404

公共签名服务器已全线关闭，没有可用实例。自己搭签名服务需要协议分析能力，超出普通用户范围。

**结论**：这条路在 2026 年之后基本走不通了。

### B2. SnowLuma 官方没有 macOS 二进制

`SnowLuma` 的 release 只有 `linux-arm64` / `linux-x64` / `win-x64`。

**但这不代表 Mac 用户不能用**：它发布的 Linux arm64 版本，在 Apple Silicon 上的 Linux 容器里可以原生跑。这就是 `02-底座.md` 整套方案的前提。

## C. 容器与网络

### C1. `colima start` 卡在 `error resolving download URL ... request canceled`

首次启动要从 GitHub 下虚拟机镜像，国内基本超时。

**修法**：改用镜像加速，或者自己下载 `ubuntu-*.raw.gz` 后用 `--vm-type` / 本地缓存塞进去：

```bash
colima start --cpu 4 --memory 8 --disk 40
```

如果还不行，给 `colima` 配 `LIMA_HOME` 里的镜像缓存，见 `scripts/01-colima.sh`。

### C2. GitHub 下载慢到没法用

实测（同一个网络）：

| 方式 | 速度 |
|---|---|
| GitHub 直连 | ~30 KB/s |
| `https://ghfast.top/https://github.com/...` | ~720 KB/s |
| `https://gh-proxy.com/https://github.com/...` | ~82 KB/s |

**但注意**：`ghfast.top` 对部分包会返回 24 字节的 `Forbidden by black list.` 直接拒绝。脚本里要写**失败自动直连**的回退，不要硬编码一个镜像。

### C3. 容器里访问不到宿主机文件

**报错**：`ENOENT: no such file or directory, open '/Users/you/audio.mp3'`

**原因**：容器有自己的文件系统，宿主机路径在容器里不存在。

**修法**：不要传路径，**传 base64 内联**。播放一下思路：

```js
// 错误：容器看不到 /Users/...
{ file: '/Users/you/audio.mp3' }

// 正确：读到内存里，编码后传
{ file: `base64://${fs.readFileSync(localPath).toString('base64')}` }
```

这是本项目语音功能能跑通的关键一步。`patches/0001` 里就是这么改的。

## D. OneBot 认证

### D1. `retcode: 1401, wording: "unauthorized"`（发送消息时）

**看起来是**：token 填错了。

**真正原因**：SnowLuma 给 **HTTP 和 WS 分别生成了不同的 accessToken**，而 qq-bridge 只有一个 `accessToken` 字段。用 WS 的 token 去调 HTTP 接口，必然 401。

**修法**：把 HTTP 和 WS 的 token 设成**同一个值**。注意 SnowLuma 有两个配置文件：

```
/app/data/config/onebot.json              ← 模板，改了没用
/app/data/config/onebot_<你的QQ号>.json    ← 真正生效的
```

改错文件会让你怀疑人生。

### D2. 工具全部返回 `session/model-unavailable: Select an available model before sending a message`

**原因**：配置文件里的 provider id 写错了。provider 的 id 必须是 DSH 里**已经存在的那个**（比如 `deepseek-account`），不是随便起的名字。

**修法**：先 `GET /api/v1/config-profiles/default` 看现有 provider 的 `id` 是什么，再填。

## E. qq-bridge 与 DSH

### E1. AI 说「语音工具未开启」，但配置里 `voice.enabled` 是 true

**真正原因**：MCP 工具是**条件注册**的：

```js
// src/mcp-snowluma-safe.js
if (cfg.socialV2?.voice?.enabled !== false && cfg.socialV2?.tools?.sendVoice !== false) {
  server.tool('qq_speak', ...)
}
```

开关是 false 的时候，工具**压根没注册**，AI 在工具清单里看不到它——所以它会说"未开启"，而不是"调用失败"。

**修法**：改完 config.json 之后**必须重启 MCP server**。DSH 会自动把它拉起来。

同理适用于所有「改配置没反应」的情况：**配置是进程启动时读的**。

### E2. `execFileAsync is not defined`

补丁里用了 `execFileAsync` 但忘了定义。在 `src/bridge.js` 顶部加：

```js
const execFileAsync = promisify(execFile);
```

### E3. 控制台打不开 / 401

控制台鉴权**不是** `Authorization: Bearer`，而是：

```
x-console-token: <token>
# 或者
?token=<token>
```

token 在 `state/console-token`。

## F. 语音

### F1. `Reference audio is outside the 3-10 second range`

GPT-SoVITS 的**硬限制**：参考音频必须 3–10 秒之间。

**实测经验**：

| 素材长度 | 效果 |
|---|---|
| < 3 秒 | 声音飘，不像 |
| 6–8 秒，一句话说完整、无背景音 | **最稳** |
| > 10 秒 | 直接报错 |

裁的时候注意：降噪会让音频**变慢**，7.8 秒的素材降噪后可能变成 8.4 秒，别卡在 10 秒边缘。

### F2. 合成出来大舌头 / 含糊

**真正原因**：`prompt_text`（参考音频对应的文字）和音频**对不上**。模型必须知道那段音频说了什么，才会跟着学发音。

**排查方法**：用 Whisper 转写一遍你自己的参考音频，和 `promptText` 逐字对比。实测发现手写的文字经常漏字或错字。

### F3. 合成的语音复读 / 只说一半

**原因**：台词文本**没在参考音频里出现过时**，模型容易越界复读。

**实测数据**：

| 参考 4.39s，台词 | 结果 |
|---|---|
| 38 字 | 11.84 秒，复读 ✅ 失败 |
| 19 字 | 3.16 秒，正常 ✅ |

**规律**：**台词长度不要超过参考音频时长的 2 倍**。参考 7 秒就别写超过 14 秒的台词。

### F4. `spawn ffprobe ENOENT`

GPT-SoVITS 和 qq-bridge 都要探测音频时长，Mac 上没装 ffmpeg 就报这个。

**修法**：`brew install ffmpeg`。或者像本项目的语音实验室一样，**让浏览器解码**（Web Audio API → WAV），彻底不需要 ffprobe。

## G. 表情包

### G1. `图地址解析到内网被拦截`

**看起来是**：网络问题 / 墙。

**真正原因**：卡片的 SSRF 防护会拒绝解析到私有 IP 的 URL。但很多代理软件（Clash 的 fake-ip 模式等）会把**所有域名**解析成 `198.18.x.x` 这类保留地址——于是正常的公网图片也被当成内网地址拦掉。

**修法**：把 `198.18.0.0/15` 这类 fake-ip 网段加进白名单（见 `patches/0004-safe-fetch-fakeip.patch`），或者关掉 fake-ip 模式。

### G2. 表情包下载一直超时

用的是 GitHub 直链。同 `C2`，加镜像 + 回退。

## H. 一些非报错但很浪费时间的点

- **DSH Desktop 的 Web API 端口 = GUI 端口，每次重启都变**。脚本里别写死，要动态探测。
- **`pnpm install` 其实很快**（实测 1–6 秒）。如果你的插件市场显示「更新中…」卡很久，去看 `~/.dsh/profiles/desktop/.plugin-manager/logs/operation-*/pnpm.log`——大概率早就 `Done` 了，是界面卡住。
- **重启 DSH 之后 MCP 工具清单才会刷新**。改了工具注册条件、装了新插件，都要重启。
- **改 preset 提示词也要重启 DSH**。preset 是会话创建时读的，热改不生效。
